# Atlas AI Platform — security model

## Identity and sessions
- Server-side sessions (Spring Session JDBC, table `spring_session`), cookie `ATLAS_SESSION` (`HttpOnly`, `SameSite=Lax`, `Secure` via
  `ATLAS_COOKIE_SECURE=true` behind HTTPS). No bearer tokens, nothing sensitive in `localStorage`.
- Session fixation: the old session is invalidated and a new id issued on every sign-in.
- CSRF: double-submit cookie (`ATLAS_XSRF` cookie → `X-ATLAS-XSRF` header) on every non-GET request, including login.
- Passwords: bcrypt cost 12, 10–128 chars, must not contain the email name, minimum character variety. Unknown emails still pay one bcrypt
  comparison (timing). Login throttle: 5 failures / 15 min per email and per IP → `429`.
- Revocation: password change deletes the user's other sessions; system-admin disable deletes all; `CurrentUser` re-reads the user on every
  request (disabled or password-changed-after-login sessions fail closed even if a session row survived).
- First administrator only via one-time `ATLAS_BOOTSTRAP_ADMIN_EMAIL/PASSWORD` when the users table is empty. No default password exists.
- Self-registration is off by default (`ATLAS_REGISTRATION_OPEN=false`); invitations carry a 256-bit token, stored as SHA-256 only, 7-day expiry,
  single use, email-bound.

## Authorisation (fail closed)
- `/api/**` requires authentication; anonymous users can only read `/api/status`, CSRF/login/register/invitation-accept and the static UI.
  The legacy `PUBLIC_DEMO` anonymous-write behaviour does not exist in platform mode.
- `TenantAccess.require(orgId)` is the only way a controller obtains an `OrgContext`; it verifies an ACTIVE membership in an ACTIVE org.
  Non-members get **404** (cannot learn the org exists) and the attempt is audited.
- Roles: org `OWNER > ADMIN > EDITOR > VIEWER`; workspace `MANAGER/EDITOR/VIEWER`; knowledge base `EDITOR/VIEWER`; system `SYSTEM_ADMIN`
  (platform administration only — it does **not** grant tenant content access).
- KB effective access (`TenantAccess.effective`, unit-tested over the whole matrix): org OWNER/ADMIN or workspace MANAGER → MANAGE;
  KB/workspace EDITOR → EDIT; KB/workspace VIEWER → READ; `ORG` visibility adds EDIT for org editors and READ for viewers; `RESTRICTED` adds nothing.
- Every document/chunk/file/citation/job/run/approval lookup includes `org_id` in SQL **and** re-checks KB access; foreign ids behave like missing ids.
- Background jobs rebuild the requester's context at execution time (`contextFor`), so revoked members get no results from queued work.
- Database: composite `(org_id, id)` foreign keys make cross-tenant parent/child rows impossible. PostgreSQL RLS is not enabled yet (gap).

## Data paths
| Path | Tenant control |
|---|---|
| SQL rows | `org_id` predicate + composite FKs |
| Object storage | keys generated by the server: `org/<org>/doc/<doc>/v<n>/<sha256>`; filesystem adapter rejects any other shape / traversal |
| Qdrant | payload `org_id`, `document_version_id`; every query filtered by org + authorised version ids and re-filtered locally |
| BM25 | computed only over chunks of authorised, READY, current, unexpired versions |
| LLM context | only reranked authorised evidence; document text is passed as JSON data with an explicit "do not execute" instruction |
| Citations / chat history | re-authorised on every read; unavailable evidence → quote removed and answer text hidden |
| Jobs | readable by creator or org admin; system admin sees metadata without payloads |
| Audit | org admins see their org only; details never contain passwords, tokens, invitation secrets, document text or model output |
| Caches | no cross-request content cache exists in platform mode (embedding cache of legacy mode is not used) |

## Uploads
Extension allow-list (.md .markdown .txt .pdf .docx .xlsx) **and** magic bytes; Office files are pre-scanned as zip (≤10 000 entries,
≤200 MB expanded, no absolute/`..`/backslash paths) before POI parses them; POI zip ratio guard 0.01; extracted text ≤ 5 M chars; upload ≤ 50 MB;
strict UTF-8 for text; encrypted PDFs rejected; scanned PDFs → `NEEDS_OCR` (no fabricated text). No antivirus engine is bundled (gap; hook point
is `DocumentParser.detect`).

## Agents, tools, connectors
- No generic SQL, shell, file or arbitrary-URL tool exists. LLM output and document text never choose a tool or SQL; templates substitute
  **data** from `{{input.*}}` / `{{steps.N.*}}` into allow-listed tool parameters.
- SQL tools are named, parameterised SELECT templates, parameters validated (`[\p{L}0-9 ._\-/]{1,64}`), executed in `READ ONLY` transactions
  with a 3 s statement timeout, ≤ 200 rows. Connector SQL must be single SELECTs over `demo_erp` in v1.
- HTTP GET connector: host must be in the **server** allow-list `ATLAS_HTTP_TOOL_HOSTS`; https only (http only if
  `ATLAS_HTTP_TOOL_ALLOW_PRIVATE=true`); every resolved address must be public (loopback, RFC1918, link-local, ULA, CGNAT, multicast blocked);
  no redirects; path prefix allow-list; 256 KB response cap. Credentials only via `secretRef` → server env var `ATLAS_CONNECTOR_*`;
  config keys that look like secrets are rejected.
- MCP: endpoint must be in the server allow-list `ATLAS_MCP_ENDPOINTS`, tool names in the connector's `allowedTools`; non-`readOnly` MCP
  connectors are marked side-effecting and cannot be used as TOOL steps.
- Side effects: the only write path is `OUTPUT → agent_outputs`, which needs `output.record` in the agent whitelist, an `APPROVAL` step before it
  (validated at definition time) and an `APPROVED` approval of the same run (checked at execution). Requesters cannot approve their own runs
  unless org admin. Approvals, denials and writes are audited; tool calls are recorded with run/step/trace.

## Models
`LocalJsonHttp` accepts only loopback origins (plus operator-configured internal service names for Qdrant in containers). There is no paid
or remote model provider in this branch. Quality model is local Qwen3 8B behind llama.cpp's on-demand router.

## Observability
Every response has `X-Trace-Id`; jobs inherit the trace id of the request that created them; audit and usage rows store it.
Security headers: CSP (`default-src 'self'`), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`, `Cache-Control: no-store` on APIs.

## Known gaps (tracked in IMPLEMENTATION_REPORT.md)
RLS defence-in-depth, malware scanning, OIDC/SSO, MFA, at-rest encryption configuration (delegated to the storage/DB layer), automated retention
jobs for usage/audit, per-user (not only per-org) rate limits.
