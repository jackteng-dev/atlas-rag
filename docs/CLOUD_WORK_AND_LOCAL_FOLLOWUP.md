## Cloud 與本機分界

| 工作 | Codex Cloud 可先做 | 需留待可用本機／設備或外部條件 |
|---|---|---|
| 系統設計與程式 | 狀態機、資料結構、API 契約、前後端、角色規則、測試、文件 | 不需為寫程式先搬到本機 |
| Atlas 登入 | 合成文件與專用展示帳號、真實登入／登出、越權 API／來源／RAG 測試、HTTPS 瀏覽器展示 | 搬回本機、首次模型下載、實際帳號設定與個人文件匯入 |
| SQL／Redis／Queue | 專案隔離服務可用時跑整合測試；若環境不足，先完成程式與測試並標示未執行 | 不因 Cloud 缺 Docker 就直接標成本機必做；先記錄真正缺少的能力，再於適用環境補驗證 |
| Web／App | 共享 API、跨端業務規則、Web 展示、App 專案與可執行的單元／建置測試 | 真機操作、推播、深層連結、相機、網路切換、背景／前景切換；iOS 簽名與發佈需相應 Apple 環境 |
| 付款／LINE | Adapter、簽章驗證、重送／亂序、合成回呼與契約測試 | 商家／測試帳號、合法憑證與真實供應商 sandbox／設備；取得帳號後仍可在 Cloud 做部分整合，不要求一定本機 |
| 效能 | 隔離且有資源上限的併發／排隊／重送測試；記錄 CPU、RAM、資料庫与測試條件 | 使用者實際機器的容量、長時間測試、跨設備／網路；Cloud 數字不可推定本機吞吐量 |
| 最終展示 | 臨時 HTTPS、瀏覽器操作錄影／截圖、可重現啟動工具 | 同機多專案整合、連接埠、反向代理、外部可連方式、持續運行與備份還原 |

Cloud 本身只有臨時測試用途，不能把通道可連當成正式 uptime 或固定域名。外部 HTTP／WSS 使用 inherited proxy／CA，保留 TLS 驗證；不改全域資料庫、網路政策或其他專案程序。未授權付費模型、服務或商店發佈。

## 發呆亭：依營運動作收斂權限

保留角色式授權；ADMIN／STAFF 仍是 RBAC。調整的是實際不需要的粒度，不是撤掉後端 API 檢查。以下是待和現有流程核對的草案，不聲稱已改碼。

| 動作 | ADMIN（營運負責人） | STAFF（現場人員） |
|---|---|---|
| 查看預約、營位與必要入住資料 | 可 | 可；只暴露工作所需個資 |
| 報到／退房、必要聯繫紀錄 | 可 | 可 |
| 商品／營位／價格／付款／LINE 設定 | 可 | 預設不可 |
| 退款、敏感訂單變更 | 可 | 預設不可；若實際有需求再單獨授權 |
| 帳號與角色設定 | 可 | 不可 |

Cloud 可做：盘點路由／API／資料存取、形成矩陣、依矩陣改前後端、直接 API 越權測試、退回舊權限配置的遷移方案。移除細粒度功能前先查使用依賴与資料，不能直接刪表或讓舊帳號意外升權。付款重送需以真實資料庫唯一約束／交易與重複事件測試驗證，不能只依 README 描述。

## ELPSY Shop：正式電商與 App 共用後端

不把 ELPSY Shop 重新定位成只有授權 Demo。Web 與 App 共用商品、價格、庫存與訂單規則；角色、部門／倉庫範圍在有真實營運需求時才加入。

Cloud 依序完成：

1. 盤點既有後端／Web／App 與 API；選擇並記錄 App 技術，避免假設 Flutter／React Native／原生已有實作。
2. 統一商品、金額精度／幣別、價格快照、訂單狀態與錯誤契約；服務端為業務規則來源。
3. 在目標資料庫驗證購物車結帳、庫存、付款事件冪等、重試與回滾；H2 與 mock 測試不能代替 PostgreSQL／實際目標資料庫證據。
4. 補必要的 CUSTOMER／ADMIN／營運角色，依訂單所有權限制買家；客服與倉庫權限按實際流程再加。
5. Web 與 App 的核心購物路徑、登入更新／過期、API 契約與可執行的建置／測試。
6. 再驗證付款供應商 sandbox、退款／退貨、發貨、通知與監控。

正式電商是發展目標；完成模擬付款或 App 編譯，不等於可收真實款或可商店發佈。

## 搶票網站：先驗證不超賣，再加排隊架構

建議獨立作品，初始以單一活動、限量名額與模擬付款為範圍。指定座位、跨場次、轉讓、真實金流等另列後續，不一次加入全部功能。

第一階段的核心規則：

- 同一張票／同一名額最多只屬於一筆有效保留或售出；任何時點有效保留 + 售出不超過總量。
- 同一帳號、同一冪等鍵、相同內容重試得到同一結果；同鍵不同內容拒絕。
- 保留到期後可再售；付款成功與到期回收競爭時只允許一個有效狀態轉移。
- 客戶端不能繞過服務端售票時間、配額、入場資格或訂單所有權。

建議實作順序：

1. PostgreSQL 交易／唯一約束／條件更新，建立名額與限時保留的狀態機，先測試超額請求與重試。
2. 加入 waiting room、服務端排序與有限入場名額。Redis 可做排隊／限流／短期入場憑證，但資料庫仍保存最終訂單與售出票的事實。
3. 以穩定序號定義公平性，例如服務端成功接受的順序；分清 HTTP 抵達、取得入場資格、確認購買三個順序。顯示序號與預估等待不代表保證 FIFO 完成購買。
4. 需要可靠非同步通知／付款事件時，加入 transactional outbox + queue consumer。先選一種必要 broker；重送必須冪等，不聲稱網路具有端到端 exactly-once。
5. 測試 consumer 退出／重啟、訊息重送／亂序、Redis 暫停、保留到期與服務恢復。Web 顯示排隊進度、逾時與可重試狀態。

Cloud 初步驗收可用 100 個名額、1000 個合成購買者、受控同時連線，驗證超賣為零、庫存／訂單對帳、同鍵重試、到期回收、故障恢复。這是功能与一致性測試設計，不是承諾 1000 人吞吐或高可用；測試是否已執行需另附原始結果，不能只列技術名稱。
